# Tool-triggered authorization, October 26, 2026

## Reproduced condition

The installed personal package was 0.2.3. Its research skill was visible, but the chat exposed no BuyerCaddy tools. The configured `/mcp` endpoint required OAuth even for initialization/discovery, the manifest selected OAuth-only, and neither tool auth metadata nor native per-tool auth challenges were implemented. Instructions about Connect could not implement that missing protocol flow.

The installed cache metadata resolved the exact personal plugin ID `Plugin_18447cd8d8708191acaaca29a7e97551`; backend search and the personal inventory returned empty results, but reading this exact ID succeeded. The fetched source matched the maintained package. Scope is USER, visibility PRIVATE. No duplicate was created and no sharing settings changed.

## Correction

- Plugin 0.2.4 uses `/mcp/openai` with mixed authentication and the existing DCR/PKCE flow. Existing branding, prompts, research skill and review metadata remain.
- Gateway permits only initialization, initialized notification, ping and tool-list metadata before authentication. Tool calls return the documented OAuth challenge without reaching the data service. All tools require `mcp:tools`.
- OAuth access, refresh and code exchange remain bound to the selected resource. Discovery and private session contexts stay separate. The 0.4.1 correction creates a new private upstream session when a host retries on its discovery transport after OAuth.
- Existing `/mcp` clients retain their connection-level OAuth behavior.

## Evidence

- Gateway 0.4.1 revision `buyercaddy-oauth-gateway-00023-vok` was promoted from zero to 100% traffic after the candidate checks. Canonical discovery/auth-challenge and version checks also passed. The original endpoint still rejects unauthenticated discovery with HTTP 401.
- 29 gateway tests pass; 5 Node package tests and 8 Python packaging tests pass.
- Python and PowerShell ZIPs have identical names and uncompressed contents, 15 files. Listing, icon and default prompts are preserved.
- Live candidate and canonical discovery returns 20 tools, each declaring OAuth. An unauthenticated bounded Vendors request returns the native auth challenge, not customer data.
- A real MCP SDK completes initialize/list-tools and receives the auth challenge.
- Live DCR, consent and cancellation tests pass for ChatGPT, Claude and native callbacks, including the new exact resource. No API key was read or used.
- Personal release saved as `pluginrel_6adf70ec2c1c8191885fb929a7f7a3c2`; source read-back verifies 0.2.4, mixed auth and the new endpoint. The installed local cache subsequently updated to 0.2.4; the current running chat did not refresh its tool inventory.

## Pending host acceptance

The initial explanation that the current chat simply needed a refresh was incomplete. A later direct app-server check reproduced a parser rejection in 0.2.4; see the host compatibility correction below. Displayed UI, actual user sign-in and returned data have not been established by protocol checks alone.

## Host compatibility correction: 0.2.5

The running Codex Desktop binary is 0.164.0-alpha.11.1. Its `plugin/read` reports BuyerCaddy installed and enabled, but `mcpServerStatus/list` returned no BuyerCaddy server. The loader log identifies the exact failure:

```text
failed to parse plugin MCP server ... /buyercaddy/0.2.4/mcp.json
unknown field `extensions`, expected `url` or `headers`
```

Remove only the server-level `extensions` field in portable `mcp.json`; retain the HTTPS endpoint, server identity, skill, listing and OAuth enforcement in the gateway. Update both packaging validators and version metadata to 0.2.5. The backup of affected source files is `.verification/before-host-compat-0.2.4.zip`.

Verification with the same Codex binary and an isolated local plugin installation returns `buyercaddy`, all 20 tools, `toolsError: null` and `authStatus: notLoggedIn`. All 13 package tests pass; Python and PowerShell ZIP outputs contain the same 15 files. Personal release `pluginrel_6adf781ff47c81919ebf26ea28b61d2c` preserves USER/PRIVATE scope. Backend read-back confirms the portable and generated legacy MCP files omit the rejected extension.

The supported `plugin/install` app-server method then updated the existing personal installation to 0.2.5 in the real Codex home. A subsequent `mcpServerStatus/list` in that profile returns `pluginId: buyercaddy@created-by-me-remote`, all 20 tools, `toolsError: null`, `authStatus: notLoggedIn`. This verifies discovery of the actual installed personal plugin, beyond the isolated package test. The already running conversation's tool inventory and the settings panel rendering remain separate UI checks.
